# PRD: Personal Brain V1 slice 1 — 수집하고, 적어 두고, 찾는다

## 0. Document Purpose

이 문서는 Personal Brain의 첫 조각이 **무엇을 해야 하는지**를 정한다. 독자는 나(명훈)와 이 문서를 이어받는 BMad 스킬(architecture, spec, ticket, build)이다. 어떻게 만드는지(테이블, 모델, 파이프라인 수치, 에이전트에게 기록을 시키는 수단)는 `addendum.md`에 있고 architecture 단계의 입력이다.

기반 문서는 `../brief-personal-brain/brief-personal-brain.md`와 그 addendum §9(사전 시험 6회), 그리고 처음의 아키텍처 초안 `../inputs/personal-brain-final-architecture.md`다. 이 PRD는 그것을 반복하지 않는다. 용어는 §3 Glossary를 그대로 쓰고, 기능(§4)마다 요구사항을 FR-1부터 전역 번호로 매긴다. 확인받지 않고 추정한 곳은 `[ASSUMPTION]`으로 표시하고 §10에 모았다. 모든 FR이 전제하는 제약은 §9에 있으니 §4보다 먼저 본다.

## 1. Vision

새 세션을 열어도 Brain은 내가 어제 무엇을 했는지 안다. 나는 규칙을 한 번만 말하고, 예전 결정을 물으면 그때의 대화 원문까지 내려가 확인할 수 있다. 어떤 에이전트를 쓰는지는 상관없다.

Brain은 **나라는 사람의 기억**이다. 프로젝트는 그 아래에 있다. 무엇이든 먼저 나의 기억에 들어가고, 프로젝트에서 한 일이면 그 프로젝트의 꼬리표가 함께 붙는다. 코딩만을 위한 것이 아니다.

slice 1은 그 최소 형태다. Claude Code의 **세션**을 자동으로 **수집**해 대화 원문을 그대로 남긴다. 일하는 에이전트가 진행·결정·규칙·선호를 그 순간에 **작업 로그** 한 줄로 적고, 그 줄은 대화 원문에 이어져 있다. 찾을 때는 넓은 것(작업 로그)부터 보고 필요하면 좁은 것(**조각**, 원문)으로 내려간다. 새 세션에는 **규칙**과 최근 작업 로그 몇 줄만 자동으로 들어가고, 나머지는 물을 때 꺼낸다.

원문은 고쳐 쓰지 않는다. Brain은 스스로 LLM을 부르지 않는다. 적는 것은 그때 일하고 있던 에이전트이고, 색인은 원문 위에 얹은 길잡이일 뿐이다. 기억은 내 것이다. 내 기계에 보관되고, 통째로 내보내고 되살릴 수 있다.

## 2. Target User

### 2.1 Jobs To Be Done

- 새 세션에서 "어디까지 했더라"를 다시 설명하지 않고 바로 이어서 일하고 싶다.
- "어제", "지난주", "작년 3월"에 무엇을 했는지 물으면 답을 받고 싶다. 프로젝트를 가리지 않고.
- 작업 규칙을 한 번만 말하고 싶다.
- 예전에 왜 그렇게 결정했는지, 그 문서가 어디 있었는지 찾고 싶다. 요약이 아니라 그때 실제로 한 말로 확인하고 싶다.
- 결정이 바뀌어도 예전 결정이 사라지지 않았으면 한다.
- 결정을 따로 정리하는 수고 없이, 일하는 중에 저절로 남았으면 한다.
- 내가 무엇을 좋아하고 어떤 상황인지를 에이전트가 필요할 때 찾아볼 수 있었으면 한다.

### 2.2 Non-Users (slice 1)

나 이외의 사용자. Claude Code 이외의 Harness로 한 작업(구조는 막지 않지만 수집 경로가 없다).

### 2.3 Key User Journeys

- **UJ-1. 명훈이 아침에 새 세션을 연다.** 어제 `acme-api`에서 세 세션을 했다. 오늘 같은 폴더에서 Claude Code를 열면, 묻지 않아도 내 규칙과 이 프로젝트의 최근 작업 로그 몇 줄이 컨텍스트에 들어와 있다. "어제 하던 거 이어서"라고만 하면 에이전트가 이어간다. **Edge**: Brain이 꺼져 있으면 세션은 평소대로 열리고, 주입이 없었다는 기록이 남는다.
- **UJ-2. 명훈이 "지난주에 뭐 했지"라고 묻는다.** 에이전트가 Brain에 날짜 범위로 물어 그 주의 작업 로그를 프로젝트를 가리지 않고 시간순으로 받는다. 기록이 없으면 "없음"이라고 답한다. 한 줄이 궁금하면 그 줄에 이어진 대화 원문을 읽어 자세히 답한다.
- **UJ-3. 명훈이 "passkey recovery를 왜 그렇게 했지, 그 문서 어디 있더라"라고 묻는다.** 에이전트가 먼저 작업 로그에서 관련 결정을 찾고, 그 줄에 이어진 대화를 읽는다. 로그에서 안 잡히면 대화 조각을 검색한다. 문서는 그 세션의 도구 메모에서 경로로 나온다. 결과마다 출처가 붙어 있어, 부족하면 앞뒤 조각이나 세션 전체를 더 읽는다.
- **UJ-4. 명훈이 "코드 리뷰 후 바로 고치지 말고 계획부터 세워"라고 말한다.** 에이전트가 이 발화를 규칙으로 표시한다. 저장되는 것은 내가 한 문장 그대로다. `acme-api`에서 한 말이지만 다음 세션부터 어느 프로젝트에서든 자동으로 들어온다. "이건 이 프로젝트에서만"이라고 하면 그 프로젝트에서만 들어온다. **Edge**: 에이전트가 규칙이 아닌 말을 규칙으로 표시했으면, 나는 목록에서 그것을 끈다.
- **UJ-5. 명훈이 결정을 바꾼다.** "임베딩 차원은 2560"이라는 결정이 로그에 있었는데 대화 중에 1024로 바꾼다. 에이전트가 새 결정을 적으면서 예전 결정을 대체한 것으로 잇는다. "왜 1024지"에는 새 결정이, "처음엔 뭐였지"에는 예전 결정이 답한다. 둘 다 근거 대화로 이어진다.
- **UJ-6. 명훈이 키보드를 조사한다.** 코드 저장소가 아닌 곳에서 세션을 열어 스위치를 비교하다 "나는 로우피치가 좋아"라고 말한다. 에이전트가 이를 선호로 적는다. 이 세션은 프로젝트 없이 나의 기억에 바로 들어간다(워크스페이스 "Keyboard"에 넣어 두는 것은 slice 1 밖, 2026-10-15). 나중에 `acme-api`에서 일하다 "전에 본 키보드 뭐였지, 내가 뭘 좋아한다고 했지"라고 물어도 찾을 수 있다. 이 선호는 매 세션 자동으로 들어오지는 않는다.

## 3. Glossary

- **Brain** — 이 시스템. Core와 Runtime, 저장소를 합친 것.
- **Core** — Brain의 기능을 가진 부분. SDK로 호출한다. 스스로 실행되지 않는다.
- **Runtime** — Core를 초기화해 실제로 부르는 쪽. slice 1에서는 에이전트용 도구와 Claude Code 연결이다.
- **나** — 기억의 맨 위 수준. 모든 세션과 작업 로그는 항상 나에 속한다.
- **Harness** — 에이전트를 돌리는 도구. slice 1에서는 Claude Code 하나.
- **워크스페이스(Workspace)** — 내가 정한 묶음(예: Acme ⊃ acme-api, acme-member). 프로젝트를 담고, 프로젝트 없는 세션도 담을 수 있다(Keyboard). slice 1에서는 쓰지 않는다(칸만 예약, 2026-10-15).
- **프로젝트(Project)** — 저장소 하나. 자동으로 식별된다. 세션에 프로젝트가 없을 수 있다.
- **워크트리(Worktree)** — 프로젝트 안의 작업 폴더·브랜치 하나(예: ACME-123). 자동으로 식별된다. 저장소 본체에서 일하면 워크트리가 없다.
- **꼬리표** — 세션과 거기서 나온 기록에 붙는 워크트리·프로젝트·워크스페이스 표시(slice 1은 워크트리·프로젝트만). 출처에서 자동으로 붙는다. 수준은 나 ⊃ 워크스페이스 ⊃ 프로젝트 ⊃ 워크트리 ⊃ 세션이고, 나와 세션 사이의 수준은 없을 수 있다. 기억을 가르는 칸막이가 아니라 조회를 좁히고 넓히는 손잡이다.
- **세션(Session)** — Harness에서 한 번 열고 닫은 작업 단위. 메시지 여러 개를 가진다.
- **메시지(Message)** — 세션 안에서 내가 한 말 또는 에이전트가 한 말 한 건. 본문은 원문 그대로다.
- **도구 메모(Tool Note)** — 에이전트의 도구 호출 한 건을 한 줄로 적은 것(도구 이름, 대상, 성공 여부). 도구의 출력 내용은 담지 않는다.
- **추적 정보** — 세션과 메시지에 붙는 출처 정보: Harness, 모델, Harness의 원래 세션 ID, 기계, 꼬리표, 브랜치, 시각, 이어받은 세션.
- **수집(Ingest)** — 세션의 메시지, 도구 메모, 추적 정보를 Brain에 넣는 일.
- **작업 로그(Log Entry)** — 일하는 에이전트가 그 순간에 적는 한 줄. 종류는 **진행**, **결정**, **규칙**, **선호** 넷이다. 대분류 색인이다.
- **진행(Progress)** — 작업 로그의 한 종류. 한 일 한 단계.
- **결정(Decision)** — 작업 로그의 한 종류. 내가 내린 결정 한 건(FR-20).
- **규칙(Rule)** — 작업 로그의 한 종류. 내가 한 말 중 앞으로 지켜야 할 작업 규칙(FR-19).
- **선호(Preference)** — 작업 로그의 한 종류. 나에 대한 사실(좋아하는 것, 상황)(FR-21).
- **적용 범위** — 규칙이 주입되는 곳. 기본은 어디서나이고, 한 프로젝트로 제한할 수 있다. 꼬리표(출처)와는 별개다.
- **조각(Chunk)** — 연속한 메시지 몇 개를 묶은 검색 단위. 소분류 색인이다.
- **대분류 / 소분류** — 조회의 두 단계. 대분류는 작업 로그, 소분류는 조각이다.
- **출처(Source Pointer)** — 작업 로그와 조각이 가리키는 근거 세션과 그 안의 대화 위치.
- **시작 맥락** — 세션이 시작될 때 Brain이 자동으로 넣는 묶음: 켜져 있는 규칙, 최근 작업 로그 몇 줄, Brain 사용 안내.
- **조회(Recall)** — 내가 묻거나 에이전트가 필요하다고 판단해 Brain에서 과거를 찾는 일. 시간 조회, 대분류 검색, 소분류 검색, 넓히기를 포함한다.

## 4. Features

### 4.1 세션 수집

**Description:** Claude Code 세션을 Brain이 수집한다. 내가 할 일은 없다. 대화 본문은 그대로, 도구 호출은 도구 메모로, 출처는 추적 정보로 남는다. Orca와 Paseo는 Claude Code를 감싸는 도구이므로, 그 안에서 돌린 Claude Code 세션도 Claude Code 세션으로 수집된다. `[ASSUMPTION]` 모든 UJ의 전제.

#### FR-1: 대화 원문 수집
Brain은 Claude Code 세션의 모든 메시지를 본문 그대로 저장한다.

**Consequences (testable):**
- 세션의 내 발화와 에이전트 발화가 순서와 시각을 유지한 채 전부 조회된다.
- 저장된 본문은 Harness가 보여 준 텍스트와 글자 단위로 같다. 요약·번역·절단이 없다. 예외는 내가 요청한 저장본 가리기(FR-26) 하나다. 알려진 비밀은 저장할 때가 아니라 나갈 때 가린다(2026-10-18).
- 수집에 LLM 호출이 없다.

**Out of Scope:** 도구의 출력 내용, Harness 원본 transcript 파일 보관, 서브에이전트의 대화와 보고(2026-10-15에는 최종 보고 하나를 남기기로 했으나 2026-10-21에 뺐다. 결론은 메인 에이전트의 답으로 남는다). 대화에 붙인 첨부는 FR-27이 맡는다.

#### FR-2: 도구 메모
Brain은 세션의 도구 호출마다 도구 메모 한 줄을 저장한다. Realizes UJ-3.

**Consequences (testable):**
- 파일을 고친 세션에서 "어떤 파일을 다뤘나"가 도구 메모만으로 나온다.
- 파일 경로나 이름으로 도구 메모를 찾아, 그 파일을 다룬 세션들을 얻을 수 있다.
- 도구 메모 한 건은 한 줄이고, 도구 출력 본문을 포함하지 않는다.

#### FR-3: 추적 정보
Brain은 세션과 메시지에 추적 정보를 기록한다.

**Consequences (testable):**
- 임의의 메시지에 대해 어느 Harness, 어느 모델, 어느 세션, 어느 기계, 어느 프로젝트·워크트리·브랜치, 언제였는지 답할 수 있다.
- Harness의 원래 세션 ID로 Brain의 세션을 찾을 수 있다.
- 세션이 다른 세션을 이어받았다는 관계를 기록할 자리가 있다. `[ASSUMPTION: slice 1에서는 자리만 두고 자동으로 채우지 않는다]`
- Harness에 고유한 값은 추적 정보 안에만 있다. 조회와 작업 로그의 동작은 어느 Harness의 세션인지에 따라 달라지지 않는다.

#### FR-4: 나, 워크스페이스, 프로젝트, 워크트리
모든 세션은 나에 속하고, 워크트리·프로젝트가 있으면 그 꼬리표가 함께 붙는다. 워크스페이스는 slice 1에서 쓰지 않는다(칸만 예약, 2026-10-15).

**Consequences (testable):**
- 저장소 안에서 세션을 하면 그 저장소가 프로젝트로 자동 식별된다. 처음 보는 저장소면 프로젝트가 생긴다.
- 저장소가 아닌 곳에서 한 세션은 프로젝트 없이 수집되고 조회된다. 목록에서는 "기타"로 보인다.
- 같은 저장소의 다른 워크트리에서 한 세션은 같은 프로젝트로 묶이고, 워크트리 꼬리표가 따로 남는다. 워크트리 하나로 좁혀 조회할 수 있다.
- 워크트리 폴더가 지워진 뒤에도 그 워크트리의 세션과 기록은 그대로 조회된다.
- (slice 1 밖, 2026-10-15) 나는 프로젝트를 워크스페이스에 넣을 수 있고, 프로젝트 없는 세션도 워크스페이스에 넣을 수 있다. 회사/개인 같은 경계는 내보내기·지우기·팀 공유를 경계 단위로 할 때 정한다.
- 세션에서 나온 작업 로그와 조각은 그 세션의 꼬리표를 따른다. 꼬리표는 첫 메시지의 위치(cwd)로 한 번 정해지고 바뀌지 않는다(2026-10-15).

#### FR-5: 빠짐없이, 중복 없이
Brain은 같은 세션을 여러 번 수집해도 한 번만 저장하고, 수집 실패를 드러낸다.

**Consequences (testable):**
- 같은 세션을 두 번 넣으면 메시지 수가 늘지 않는다.
- 이어서 연(resume) 세션은 새 메시지만 추가된다.
- 수집이 실패한 세션은 목록으로 확인할 수 있고 다시 수집할 수 있다. 다시 수집은 Harness가 그 세션의 기록을 갖고 있는 동안에만 가능하다(Claude Code는 기본 30일 뒤 지운다). 그 기한이 가까운 미수집 세션은 점검에서 경고된다.
- Brain이나 저장소가 꺼져 있어도 Claude Code 사용은 막히지 않는다.

#### FR-6: 수집 경로의 구분
Brain은 실시간으로 수집한 세션과 나중에 가져온 세션을 구분해 담는다.

**Consequences (testable):**
- 세션마다 수집 경로(실시간/가져오기)와 수집 시각이, 메시지마다 원래 발화 시각이 따로 기록된다.
- 발화 시각이 과거인 세션을 넣어도 시간 조회(FR-12)는 수집 시각이 아니라 발화 시각으로 답한다.

**Out of Scope:** 가져오기 기능 자체(§6.2).

### 4.2 작업 로그

**Description:** 일하는 에이전트가 한 단계가 끝났거나, 결정이 났거나, 내가 규칙이나 선호를 말했을 때 그 순간에 한 줄을 적는다. BMad의 memlog와 같은 방식이다. 뒤에서 따로 요약을 돌리지 않는다. 적힌 줄은 그것이 나온 대화에 이어져 있어, 한 줄에서 원문으로 바로 내려간다. Realizes UJ-1~6.

#### FR-7: 그 순간에 한 줄
에이전트는 세션 중에 작업 로그를 적을 수 있다.

**Consequences (testable):**
- 종류는 진행, 결정, 규칙, 선호다.
- 적는 데 Brain의 LLM 호출이 없다.
- 적힌 줄은 적은 세션, 적은 시각, 적은 모델, 세션의 꼬리표를 자동으로 가진다.
- 수집보다 먼저 적혀도 된다. 그 세션의 메시지가 아직 Brain에 없어도 작업 로그는 저장되고, 수집된 뒤에 대화와 이어진다.

#### FR-8: 로그는 대화에 이어져 있다
작업 로그 한 줄에서 그 줄이 나온 대화로 갈 수 있다.

**Consequences (testable):**
- 한 줄을 고르면 그 줄이 적힌 시점 앞뒤의 메시지를 읽을 수 있다.
- 한 세션의 작업 로그를 시간순으로 모아 볼 수 있다.
- 작업 로그를 고치거나 꺼도 메시지 원문은 변하지 않는다.

#### FR-9: 로그가 없어도 세션은 보인다
작업 로그가 한 줄도 없는 세션도 시간 조회와 목록에 나타난다.

**Consequences (testable):**
- 그런 세션은 꼬리표, 시각, 첫 요청 문장, 다룬 파일(도구 메모)로 표시된다.
- 로그가 없는 세션의 수를 확인할 수 있다(SM-4).

**Out of Scope:** Brain이 LLM으로 세션을 요약하는 것(§8-1).

### 4.3 색인

**Description:** Brain은 메시지를 조각으로 묶고, 조각과 작업 로그를 의미 검색이 되게 한다. LLM을 쓰지 않는다. Realizes UJ-3, UJ-6.

#### FR-10: 조각 색인
Brain은 세션의 메시지를 조각으로 나누어 검색 가능하게 만든다.

**Consequences (testable):**
- 조각은 메시지 경계를 지키고, 각 조각은 출처를 가진다.
- 메시지 하나가 조각 크기 목표를 넘으면 나누어 담는다. 조각 크기에는 상한이 있다(값은 `addendum.md` §1).
- 조각 본문은 원문 그대로다. 프로젝트 이름이나 날짜를 본문에 덧붙이지 않는다.

#### FR-11: 다시 만들 수 있는 색인
색인은 저장된 원문과 작업 로그만으로 전부 다시 만들 수 있다.

**Consequences (testable):**
- 색인을 비우고 다시 만들어도 원문, 작업 로그, 출처는 변하지 않는다.
- 색인된 것마다 어떤 색인 설정(임베딩 모델, 차원 등)으로 만들어졌는지 기록한다. 설정이 바뀌면 옛 설정으로 만든 것을 가려내 다시 만들 수 있다.
- 다시 만든 뒤 채점표(SM-3) 점수가 다시 만들기 전보다 떨어지지 않는다.

### 4.4 조회

**Description:** 조회는 어느 수준에서든 시작해 위아래로 움직인다. 날짜를 물으면 그 기간의 작업 로그를, 내용을 물으면 먼저 작업 로그에서 찾고(대분류), 필요하면 대화 조각을 찾고(소분류), 더 필요하면 원문을 읽는다. 꼬리표로 좁히거나 나 전체로 넓힌다. 조회는 내가 묻거나 에이전트가 필요하다고 판단할 때만 일어난다. Realizes UJ-2, UJ-3, UJ-6.

`[ASSUMPTION: 대분류를 먼저 보는 순서가 조각을 바로 검색하는 것보다 낫다는 것은 재지 않았다. Brain은 두 단계를 각각 제공하고, 어느 것을 먼저 쓸지는 §8-5의 측정으로 정한다.]`

#### FR-12: 시간 조회
나는 날짜 표현으로 그 기간에 한 일을 조회할 수 있다.

**Consequences (testable):**
- "어제", "지난주", "9월 30일", "작년 3월"이 내 시간대 기준의 날짜 범위로 바뀐다.
- 기본으로 나 전체를 본다. 프로젝트를 가리지 않고 그 기간의 작업 로그와 세션이 시간순으로 나온다. 워크트리, 프로젝트로 좁힐 수 있다(워크스페이스는 slice 1에서 쓰지 않음).
- 해당 기간에 기록이 없으면 빈 결과를 돌려준다. 다른 기간의 것이 섞이지 않는다.
- 몇 년 전 기간도 같은 방식으로 조회된다.
- 시간 조회에 LLM·임베딩 호출이 없다.

#### FR-13: 대분류 검색
나는 내용으로 작업 로그를 찾을 수 있다.

**Consequences (testable):**
- 질의와 관련 있는 작업 로그가 관련도 순으로 나온다. 종류(결정만, 선호만 등)로 거를 수 있다.
- 꼬리표가 있는 곳에서 조회하면 가까운 것이 먼저 나온다: 같은 워크트리, 같은 프로젝트, 나 전체 순이다(워크스페이스 단계는 워크스페이스를 쓰게 될 때 더한다). 다른 프로젝트의 기록을 막지 않는다.
- 날짜 범위와 함께 쓸 수 있다("지난달에 인증 관련해서").

#### FR-14: 소분류 검색
나는 대화 조각을 내용으로 검색할 수 있다.

**Consequences (testable):**
- 특정 세션들 안으로 좁혀 검색할 수 있다.
- 나 전체의 조각을 검색할 수 있다. 작업 로그가 없는 세션의 대화도 검색된다.
- 한국어 질의로 영어 대화도 찾을 수 있다. 기본 구성(키워드 검색)에서는 에이전트가 질의를 영어·동의어로 바꿔 다시 찾는 것으로 충족하고, 그 방법은 시작 맥락 안내에 있다. 임베딩을 켜면 한 번의 질의로도 찾는다.
- 결과 조각 수와 총 길이에 상한이 있다(SM-C2).

#### FR-15: 넓히기
나는 조회 결과에서 원문 쪽으로 넓혀 읽을 수 있다.

**Consequences (testable):**
- 조각 하나에서 그 앞뒤 조각을 읽을 수 있다.
- 세션 하나의 메시지 전체를 순서대로 읽을 수 있다.
- 세션의 도구 메모를 읽을 수 있다.

#### FR-16: 출처 표시
모든 조회 결과는 출처를 가진다.

**Consequences (testable):**
- 작업 로그, 조각 어느 결과에서든 근거 세션과 그 안의 대화 위치로 이동할 수 있다.
- 결과에는 날짜와 꼬리표가 표시된다. 같은 주제의 옛 발언과 새 발언이 함께 나오면 날짜로 구분된다.

### 4.5 시작 맥락

**Description:** 세션이 시작될 때 Brain이 작은 묶음을 자동으로 넣는다. 검색도 LLM도 쓰지 않는다. 이후 프롬프트마다 자동으로 무언가를 넣지 않는다. Realizes UJ-1, UJ-4.

#### FR-17: 세션 시작 시 자동 주입
Claude Code 세션이 시작되면 Brain이 시작 맥락을 넣는다.

**Consequences (testable):**
- 시작 맥락은 세 부분이다: 켜져 있는 규칙(적용 범위가 어디서나인 것 + 현재 프로젝트인 것), 최근 작업 로그 몇 줄, Brain으로 과거를 조회하고 작업 로그를 적는 방법 안내.
- 최근 작업 로그는 가까운 것부터 채운다: 현재 워크트리, 현재 프로젝트, 없으면 나 전체.
- 크기 상한(SM-C1)은 최근 작업 로그 부분에 적용된다. 넘치면 오래된 줄부터 뺀다.
- 규칙은 전부 들어간다. 규칙 부분이 정해진 크기를 넘으면 그대로 넣되 점검에서 경고하고, 내가 규칙을 끄거나 적용 범위를 좁혀 줄인다. 다만 시작 맥락 전체에는 Harness가 받는 상한이 있다. 규칙만으로 그 상한을 넘으면 넣지 못한 규칙의 수와 그것을 보는 방법이 시작 맥락에 한 줄로 들어가고, 점검은 실패로 표시한다(2026-10-16).
- 선호는 시작 맥락에 들어가지 않는다.
- 내가 아무 지시를 하지 않아도 들어온다.
- Brain이 응답하지 않으면 세션은 주입 없이 시작되고 그 사실이 기록된다.

#### FR-18: 프롬프트마다 넣지 않는다
Brain은 세션 시작 이후 내 프롬프트에 자동으로 맥락을 덧붙이지 않는다.

**Consequences (testable):**
- 세션 시작 이후 Brain이 컨텍스트에 넣는 것은 도구 호출의 결과뿐이다.

### 4.6 규칙, 결정, 선호

**Description:** 놓치면 안 되는 것은 검색에 맡기지 않는다. 규칙, 결정, 선호는 작업 로그의 종류이지만 각자 지켜야 할 것이 있다. Realizes UJ-4, UJ-5, UJ-6.

#### FR-19: 규칙은 내 말 그대로
규칙은 내가 한 발화의 인용으로 저장되고, 켜져 있는 동안 시작 맥락에 들어간다.

**Consequences (testable):**
- 규칙의 본문은 출처 메시지에서 내가 한 문장과 글자 단위로 같다. 에이전트는 어느 발화가 규칙인지 표시할 뿐 문장을 다시 쓰지 않는다.
- 저장된 규칙은 다음 세션의 시작 맥락부터 들어온다. 내 확인을 받는 절차는 없다.
- 인용이 출처 메시지와 대조되지 않으면 그 규칙은 켜지지 않고 점검에 드러난다(NFR-2).
- 적용 범위는 기본이 어디서나다. 내가 한 프로젝트로 제한하라고 하면 그 프로젝트에서만 들어온다.
- 어느 프로젝트에서 나온 규칙인지는 꼬리표로 남는다. 적용 범위와 꼬리표는 별개다.

#### FR-20: 결정은 사라지지 않는다
결정이 바뀌면 예전 결정은 삭제되지 않고 대체됨으로 남는다.

**Consequences (testable):**
- 결정은 주제, 내용, 이유, 상태를 가진다.
- 새 결정은 자신이 대체한 결정을 가리킨다.
- 현재 유효한 결정만 조회할 수도, 변경 이력을 전부 조회할 수도 있다.
- 대체된 결정에 이어진 대화는 그대로 읽을 수 있다.

#### FR-21: 선호는 찾을 때 나온다
선호는 저장되고 조회되지만 자동으로 주입되지 않는다.

**Consequences (testable):**
- 선호는 대분류 검색에서 나오고, 종류로 걸러 전부 볼 수 있다.
- 선호가 바뀌면 새 선호가 예전 것을 대체하고, 예전 것은 남는다.

#### FR-22: 고치고 끄기
나는 작업 로그를 조회하고, 고치고, 끌 수 있다. Realizes UJ-4.

**Consequences (testable):**
- 켜져 있는 규칙, 유효한 결정, 선호의 목록을 볼 수 있다. 꼬리표로 좁힐 수 있다.
- 끈 규칙은 시작 맥락에서 빠지지만 기록은 남는다.
- 규칙의 적용 범위를 바꿀 수 있다.
- 결정, 진행, 선호의 문장을 고치면 고치기 전 내용과 고친 시각이 남는다. 여러 번 고쳐도 모두 남는다.

### 4.7 실행과 연결

**Description:** Brain의 기능은 Core의 SDK로 제공되고, 어떤 Runtime이든 그것을 초기화해 쓴다. 에이전트는 Brain이 제공하는 도구로 조회하고 적는다. 모든 UJ의 전제.

#### FR-23: SDK
Core의 모든 기능은 SDK 호출로 쓸 수 있다.

**Consequences (testable):**
- 에이전트용 도구와 Claude Code 연결은 SDK가 제공하는 기능만으로 구현된다. SDK를 거치지 않는 경로가 없다.
- 저장소, 임베딩, 재순위는 각각 교체 가능한 연결 지점 뒤에 있다. Core는 특정 제품 이름을 모른다.
- 어떤 구현을 연결할지는 Runtime이 명시적으로 조립한다. 실행 중에 구현을 찾아 불러오지 않는다.
- Core는 타이머, 서버, 프로세스를 소유하지 않는다. LLM을 부르지 않는다.

#### FR-24: 에이전트용 도구
에이전트와 나는 Brain의 기능을 도구로 쓴다.

**Consequences (testable):**
- 다음이 각각 도구로 있다: 시작 맥락 출력, 시간 조회, 대분류 검색, 소분류 검색, 도구 메모 검색, 넓히기, 문서 검색, 파일 정보와 원본 위치, 작업 로그 적기, 작업 로그의 조회·수정·끄기, 수집 실패 조회와 다시 수집, 비밀 가리기, 첨부 가리기, 재색인·재추출, 내보내기, 점검, 설치·재설정, 업그레이드, 제거.
- 출력은 에이전트가 읽기 좋은 형태와 사람이 읽기 좋은 형태를 고를 수 있다.
- 도구는 특정 Harness에 묶이지 않는다. 다른 Harness를 붙일 때 도구를 다시 만들지 않는다.

#### FR-25: 설정과 점검
나는 Brain이 필요로 하는 외부 연결을 설정하고 점검할 수 있다.

**Consequences (testable):**
- 설정 한 곳에 저장소와, 켰을 때의 임베딩·재순위 연결 정보가 있다. 키는 Brain 저장소 밖에 둔다.
- 점검은 적어도 다음을 보여 준다: 각 연결의 성공·실패, 색인 설정(모델, 차원), 미수집 세션, 실패한 수집·색인·주입·재순위, 대조되지 않은 규칙 인용, 규칙 크기 경고, 마지막 내보내기 시각.
- 재순위가 응답하지 않아 순위를 매기지 못한 조회는 결과에 그 사실이 표시된다.
- Brain의 런타임(수집, 조회, hook)은 외부 의존성을 설치하지 않는다. 연결하고 검증할 뿐이다.
- 설치 명령은 필요한 의존성과 로컬 저장소를 내 동의를 받아 설치할 수 있다. Claude Code에서는 플러그인을 켜면 첫 세션에 같은 설치가 자동으로 일어난다(동의는 플러그인 설치가 대신한다, 2026-10-15). 같은 명령을 언제든 다시 실행해 설정을 바꿀 수 있다.

#### FR-26: 비밀 가리기
대화에 들어간 API 키, 토큰, 비밀번호가 Brain 밖으로 나가지 않게 한다(2026-10-18 변경: 저장은 원문, 나갈 때 가림).

**Consequences (testable):**
- 수집은 대화를 원문 그대로 저장한다. Brain 밖으로 나가는 모든 것(시작 맥락, 조회 결과, 미러, 내보내기, 복제 대상, 임베딩·재순위 전송)에서는 알려진 비밀 패턴이 가려지고, 그 자리에는 종류만 남는다.
- 패턴을 고치면 다음 출력부터 새 패턴이 쓰이고, 이미 써 둔 미러와 복제 대상은 다시 만들어진다. 저장된 원문은 패턴 때문에 바뀌지 않는다.
- 이미 저장된 메시지에 비밀이 있으면 나나 에이전트가 그 부분을 저장본에서도 지울 수 있다. 지운 내용은 어디에도 보존되지 않고, 지운 위치·종류·시각만 남는다.
- 저장본에서 지우기는 원문을 바꾸는 유일한 경로다. 지운 세션의 미러와 이후 내보내기에도 지운 본문이 쓰인다.
- Brain의 저장소 파일에는 원문이 그대로 있다. 그 파일은 동기화 폴더에 두지 않고 나만 읽을 수 있다.

**Out of Scope:** Harness가 따로 보관하는 원본 transcript 파일.

#### FR-27: 첨부 원본 보관
대화에 내가 붙인 파일(문서, PDF, 이미지)을 Brain이 원본째 보관하고, 그 메시지와 연결한다(2026-10-14 추가).

**Consequences (testable):**
- 첨부가 있는 메시지에서 그 파일의 원본을 다시 열 수 있다. 원본 위치(로컬 경로 또는 연동된 저장소의 링크)를 받을 수 있다.
- 같은 내용의 파일은 한 번만 보관된다.
- 원본이 어디에 있든(로컬, 연동된 Drive) 기록 쪽에서는 같은 방식으로 가리킨다. 원본 위치가 바뀌어도 기록은 다시 쓰지 않는다.
- 내 기존 파일(원래 로컬이나 Drive에 있던 것)은 Brain이 옮기거나 지우지 않는다.

**Out of Scope:** Drive 연동, 기존 Drive 문서 색인, 연동 해제·새 기계 이전(이후 조각).

#### FR-28: 문서 내용으로 찾기
첨부 문서의 내용과 파일의 경로·이름으로 문서를 찾는다(2026-10-14 추가).

**Consequences (testable):**
- 텍스트가 있는 문서(txt, md, 텍스트가 있는 PDF, docx)는 본문의 단어로 찾힌다. 결과에는 문서, 위치(쪽·문단·글자 범위 등), 원본을 가리키는 링크가 붙는다.
- 폴더 이름과 파일 이름으로도 찾힌다. 사진은 경로와 촬영 일시로 찾힌다.
- 내용을 읽지 못한 문서(지원하지 않는 형식, 추출 실패)는 조용히 빠지지 않고 표시된다.
- 임베딩 없이 키워드 검색과 질의 바꾸기로 충족한다.

**Out of Scope:** OCR(스캔 PDF), HWP, Google Docs 원문, 좌표의 장소 이름 변환.

## 5. Cross-Cutting Requirements

- **NFR-1 원문 불변.** 메시지 본문은 저장 후 수정되지 않는다. 어떤 기능도 원문을 고쳐 쓰거나 지우지 않는다. 유일한 예외는 저장본에서 지우는 비밀 가리기(FR-26)다.
- **NFR-2 조용한 실패 금지.** 수집, 색인, 주입, 작업 로그 적기, 재순위의 실패는 반드시 기록되고 점검으로 드러난다. 성공으로 보이는 빈 결과나 품질이 떨어진 결과를 표시 없이 돌려주지 않는다. (사전 시험 1차에서 기억 0건이 HTTP 200으로 지나간 일의 교훈.)
- **NFR-3 Harness를 막지 않는다.** Brain의 지연이나 장애가 Claude Code의 시작과 종료를 막지 않는다. 연결에는 시간 상한이 있다.
- **NFR-4 한국어.** 조회는 한국어에서 동작해야 한다. 기본 검색(키워드)은 한국어 부분 일치로 동작한다. 임베딩·재순위를 켰을 때 영어 전용 모델로 구성되면 점검이 실패로 표시한다.
- **NFR-5 비용.** Brain은 slice 1에서 LLM을 부르지 않는다. 기본 구성의 외부 비용은 0이다. 임베딩·재순위를 켜면 수집·색인의 비용은 임베딩뿐이고, 조회의 비용은 내가 요청할 때만 든다.
- **NFR-6 보관과 전송.** 대화 원문과 작업 로그의 원본은 내 기계의 저장소에 **보관**된다. 세션별 Markdown 미러는 내가 정한 폴더에 떨어진다. 그 폴더가 동기화 폴더면 그 서비스로 나가며, 이는 내 선택이다. 기본 구성에서 Brain의 외부 **전송**은 없다. 임베딩·재순위를 켜면 조각 본문, 작업 로그, 질의가 그 서비스로 전송된다. Brain 밖으로 나가는 텍스트(미러, 내보내기, 임베딩·재순위 전송, 복제 대상)에서는 알려진 비밀이 가려진다(FR-26). 어떤 서비스로 무엇이 나가는지 설정과 점검에 드러난다.
- **NFR-7 지연.** 시작 맥락은 세션 시작을 체감할 만큼 늦추지 않는다. 시간 조회는 즉시, 내용 조회는 몇 초 안에 끝난다. 목표값은 SM-7.
- **NFR-8 꼬리표는 칸막이가 아니다.** 꼬리표는 조회의 순서와 좁히기에만 쓰인다. 꼬리표 때문에 찾을 수 없는 기록이 있어서는 안 된다.
- **NFR-9 영속성.** 나는 Brain의 모든 원문과 작업 로그를 Brain 없이도 읽을 수 있는 형식으로 내보낼 수 있고, 내보낸 것에서 되살릴 수 있다. 색인은 되살린 뒤 다시 만든다(FR-11). 되살린 뒤 메시지·작업 로그·파일·문서 추출 세대의 수가 내보내기 전과 같고, Brain이 보관한 원본 파일을 다시 열 수 있다(2026-10-16).

## 6. Non-Goals and Scope

### 6.1 Non-Goals

- 대화를 사실 문장으로 다시 써서 저장하는 기억 엔진이 아니다. 추출·통합(Hindsight 등)은 쓰지 않는다.
- Brain이 뒤에서 LLM으로 세션을 요약하지 않는다. 적는 것은 일하는 에이전트다.
- 프롬프트마다 맥락을 밀어 넣지 않는다.
- LLM이 대화를 주제별로 분류하지 않는다. 분류는 꼬리표뿐이다.
- 규칙을 Harness의 지시 파일(CLAUDE.md 등)에 복사해 두지 않는다. 규칙의 원본은 Brain 하나다.
- 코딩 전용이 아니다. 다만 slice 1의 수집 경로는 Claude Code 하나다.
- 범용 플랫폼이 아니다. slice 1은 나 한 사람, 기계 한 대다. 팀 공유는 이후 조각이다(§6.2).

## 7. Success Metrics

**Primary**
- **SM-1 이어가기.** 2주 실사용 동안, 전날 작업이 있던 프로젝트에서 새 세션을 열고 "이어서"라고만 한 횟수 중, 에이전트가 다시 설명을 요구하지 않고 이어간 비율. 목표 80% 이상(내가 그때그때 기록). Validates FR-1, FR-7, FR-17.
- **SM-2 시간 조회.** "어제/지난주/특정 날짜에 뭐 했지"라고 물은 횟수 중 답이 실제와 맞은 비율. 목표 90% 이상. 기록이 없는 기간에 "없음"이라고 답하는 것 포함. Validates FR-9, FR-12.
- **SM-3 채점표.** 사전 시험의 한국어 10문항을 실사용 데이터로 다시 채점해 7개 이상. 여기에 조각 검색이 불리한 4유형(집계, 세션 간 변화, 모순 해소, 시점 추론)을 각 2문항 추가한다. 추가 8문항 중 4개 미만이 맞으면 추출·통합 엔진 도입을 검토한다. 기본 구성(키워드 검색 + 에이전트의 질의 바꾸기)으로 재고, 목표에 못 미치면 임베딩을 켜고 다시 잰다. Validates FR-13~16, FR-20.
- **SM-4 로그가 실제로 적히는가.** (a) 작업 로그가 한 줄 이상 있는 세션의 비율, 목표 80% 이상. (b) 주 1회 세션 3개를 뽑아, 그 세션에서 내린 결정 중 로그에 적힌 비율, 목표 80% 이상. (c) 같은 표본에서, 그 세션의 작업 로그만 본 다른 에이전트가 이어서 일할 수 있겠는지를 내가 예/아니오로 기록. (a)나 (b)가 목표에 못 미치면 §8-1, §8-3을 다시 연다. Validates FR-7, FR-8.

**Secondary**
- **SM-5 수집 누락.** 이 기계에서 Claude Code가 남긴 세션 수와 Brain의 세션 수의 차이. 목표 0. Validates FR-1, FR-5.
- **SM-6 규칙.** 저장된 규칙과 같은 뜻의 말을 내가 다시 한 횟수(주 단위로 기록). 목표 주 1회 이하. Validates FR-17, FR-19.
- **SM-7 지연.** 두 가지로 잰다(중앙값). Brain 내부 처리 시간: 시작 맥락 0.5초, 시간 조회 0.1초 이내. 프로세스 시작을 포함한 전체 시간: 시작 맥락 1초, 시간 조회 0.5초, 내용 조회 3초 이내. 전체 시간은 첫 구현에서 실측해 확정한다. `[ASSUMPTION: 데몬 없이 호출마다 프로세스를 띄우는 구조에서 잡은 여유값]` Validates NFR-7.
- **SM-8 비용.** Brain의 LLM 호출 0. 외부 API 비용 월 10달러 이하 `[ASSUMPTION]`. Validates NFR-5.

**Counter-metrics (늘리려 하지 말 것)**
- **SM-C1 시작 맥락 크기.** 글자 수로 잰다(Brain은 토크나이저를 쓰지 않는다). 최근 작업 로그 부분 600자, 규칙 부분의 경고선 1,000자 `[ASSUMPTION: 300·500토큰을 한국어 기준으로 환산]`. 더 넣는다고 SM-1이 오른다는 증거가 없다. SM-1을 올리려고 이 값을 올리지 않는다.
- **SM-C2 조회 결과 길이.** 한 번의 조회 결과 8,000자 이하 `[ASSUMPTION: 기준선의 조각 5개 8,220자]`. 정답률을 올리려고 결과 수를 늘리지 않는다. 넓히기(FR-15)가 그 역할이다. Counterbalances SM-3.
- **SM-C3 작업 로그의 양.** 세션당 작업 로그 중앙값 10줄 이하 `[ASSUMPTION]`. SM-4를 올리려고 사소한 것까지 적게 하지 않는다. Counterbalances SM-4.

## 8. Open Questions

1. **LLM 세션 요약이 필요한가.** slice 1은 작업 로그만으로 간다. 로그가 없는 세션은 첫 요청 문장과 도구 메모로만 보인다(FR-9). SM-4가 목표에 못 미치거나 과거 세션 가져오기를 만들 때(옛 세션에는 로그가 없다) 세션당 요약 1회를 안전망으로 넣을지 다시 판단한다. 기준선 측정에서 요약은 시간 질문 2/2를 만들었지만 괄호·대비 절·수치를 빠뜨렸다.
2. **BMad와의 연계.** BMad의 memlog와 작업 로그는 "그 순간에 한 줄"이라는 방식이 같다. BMad 스킬이 memlog에 적을 때 Brain에도 적히게 할지, Brain이 프로젝트의 `.memlog.md`와 BMad 문서를 읽어 들일지, 따로 둘지 정하지 않았다. 종류 체계의 대응은 `addendum.md` §2.
3. **에이전트에게 기록을 시키는 수단.** 시작 맥락의 안내만으로 충분한지, AGENTS.md·skill·plugin 같은 더 강한 수단이 필요한지는 SM-4로 드러난다. 후보는 `addendum.md` §4. Harness마다 수단이 달라질 수 있다. [부분 해결 2026-10-15: 수단은 Claude Code 플러그인이고, 스킬은 Brain 안내문의 생성물이다(architecture AD-17·AD-19). 충분한지는 여전히 SM-4로 본다.] [2026-10-20: 후보 중 Stop hook 점검을 설정 토글(`[discipline] stop_remind`, 기본 꺼짐)로 더한다(`../change-discipline-and-metrics/` D1~D3). 2주 실사용의 둘째 주에 켜고 `stats show`로 SM-4a를 비교한 뒤 기본값을 정한다. 자세한 조건은 architecture AD-17.]
4. **도구의 형태.** [해결: architecture AD-5] slice 1은 CLI만 낸다. MCP는 같은 이름·입출력 규칙으로 나중에 붙인다. [2026-10-15: epic 9에서 `brain mcp serve`(stdio)로, 쓰기 도구는 세션 인자 규약(AD-28).]
5. **대분류 먼저가 실제로 나은가.** 작업 로그 검색 → 조각 검색의 2단계는 재지 않았다. 기준선에서 잰 것은 LLM 요약(6.5/8)과 조각(8/8)이고, 에이전트가 적은 작업 로그는 아직 데이터가 없다. architecture 단계와 실사용에서 같은 채점표로 비교한다.
6. **규모.** 기준선은 조각 29개였다. 2026-10-08 규모 시험(실세션 226개, 조각 5,016개)에서 파일 grep만으로 13.5/16, 임베딩+재순위 14/16이 나왔다(`addendum.md` §1). 작업 로그가 쌓인 실사용 데이터로는 아직 재지 않았다.
7. **수집 시점과 재시도의 주체.** [해결: architecture AD-6, AD-7] 턴마다 증분 수집하고, 밀린 일은 drain 하나가 다음 세션 시작과 점검 때 처리한다.
8. **에이전트가 스스로 조회하는가.** 프롬프트마다 넣지 않기로 했으므로(FR-18), 내가 "전에 하던 거"라고 했을 때 에이전트가 실제로 Brain을 조회하는지가 SM-1을 좌우한다. 모자라면 "내가 과거를 언급한 프롬프트에만 조회"를 검토한다. ## 9. Constraints

- 원본 저장소는 이 기계의 로컬 SQLite 파일 하나다. 원문, 작업 로그, 색인이 같은 곳에 있고, 설치에 서버나 Docker가 필요 없다. 다른 DB(Postgres)나 클라우드 폴더(Drive)는 원본을 따라오는 선택 복제 대상이며 slice 1 이후에 붙는다(2026-10-14 결정, `../change-local-sqlite-primary/`). 세션별 Markdown 미러는 원본에서 다시 만들 수 있는 파생물이다.
- 실행 환경은 내 Mac 한 대(운영은 집 Mac mini)다.
- 구현 언어는 TypeScript다.
- 선행 작업: 대화에 평문으로 노출된 적이 있는 Model Studio API 키를 slice 1을 설정하기 전에 다시 발급한다.
- 검색은 키워드를 기본으로 한다. 사전 시험의 기준선 구성(다국어 임베딩, 다국어 재순위)은 설정으로 켜는 선택 색인이고 기본은 꺼짐이다. 구체 모델과 측정 조건은 `addendum.md` §1.
