# 입력: 최신 제품 결정과 확인된 사실

이 파일은 2026-10-27~28 대화에서 확정한 제품 방향과 준비 과정의 관찰을 구분한다. 후속 요구사항은 여기의 ID를 인용한다. 이전 조사 문서와 충돌하면 사용자 결정 S1~S14가 우선한다.

## 사용자 결정

- S1: Garmin을 second-brain 안으로 흡수해 하나의 제품으로 만든다. Garmin 비사용자는 기능을 설치/활성화하지 않아도 된다.
- S2: 주 데이터베이스는 하나의 PostgreSQL이며 OrbStack의 Docker로 실행한다. SQLite 원본/Postgres 복제 모델을 최종 제품으로 유지하지 않는다.
- S3: 지금까지 쌓인 Garmin 데이터와 이미 분석한 결과를 이전한다. 기존 데이터 이전을 생략한다는 중간 발언은 최종 정정으로 대체됐다.
- S4: 애플리케이션 설정을 DB로 옮긴다. 대상 레포의 기존 결정처럼 사용자와 함께 이동할 설정은 DB, 기계별 설정/접속 bootstrap과 비밀은 기존 분리 원칙에 맞춘다.
- S5: 독립 작업은 병렬로 실행할 수 있다. 순서가 필요한 작업은 의존성을 유지한다.
- S6: 정상적으로 작업 중인 긴 작업은 시간이 지났다는 이유만으로 취소하지 않고 관찰하며 계속 진행할 수 있어야 한다. 오류와 실제 걸림을 구분한다.
- S7: Telegram·Slack 등은 에이전트가 먼저 말을 걸고 사용자도 답하는 공통 대화 채널로 추가할 예정이다. Garmin 전용 일방향 알림에 제품 전체를 묶지 않는다.
- S8: Drive는 아직 미구현이며 임베딩 채택은 보류한다. 우선 텍스트 검색으로 진행한다.
- S9: 에이전트가 질문에 맞는 검색어/기간/자료 종류를 선택하고 검색·원문·건강 수치 조회 기능을 호출하는 방향으로 논의했다. 정확한 API 이름과 노출 표면은 아직 설계 결정이다.
- S10: 이 요청은 흡수 준비다. 실제 데이터 반입·기존 DB 스키마 변경·Docker 기동·모델 호출·메시지 발신·플러그인 배포는 이번에 수행하지 않는다.
- S11: Garmin의 구현은 대부분 존재한다. 새 제품에서 기존 계산·분석 동작을 재사용하는 것이 목표이며, TypeScript 전체 재작성은 요구하지 않았다.
- S12: 최종 이전은 원본과 기존 AI 분석을 보존해야 한다. 기존 분석을 다시 생성하는 것으로 이전 완료를 대신하지 않는다.
- S13: Brain 플러그인에 공통 install 스킬(익스텐션 설치 안내)을 기본 제공하고, 에이전트가 Brain 설치 CLI를 호출해 확장 설치·사용자 로그인·예약 설정을 안내한다. Garmin 미설치 상태에서도 이 스킬을 사용할 수 있어야 한다. 실제 설치·버전/상태 관리는 Brain이 수행한다.
- S14: Garmin 자동 실행은 Brain의 공통 스케줄러가 구현되면 그 기능에 등록해 사용한다. Garmin 전용 스케줄러를 별도로 만들지 않는다. 공통 스케줄러가 준비되지 않았으면 자동 실행 설정 대기와 수동 실행을 구분한다.

## 준비 과정의 구현/로컬 상태 관찰

- E1: 소스 기준 Garmin `7fb33dd`, Brain `22390f5`. Garmin 코드 migration은 0016, normalize version은 8이다. Brain SQLite schema는 9이며 Postgres adapter는 health/schema 확인 수준이다. 근거: inputs/research와 소스 manifest.
- E2: 로컬 개발 DB는 schema15, 운영 후보와 이전 보관본은 schema10이다. 이번에 관찰한 DB에는 evaluation/day_summary/workout/exercise_log가 없다. 기존 분석은 Markdown·facts·이미지 등 파일에서 보존해야 한다. private manifest는 실제 관찰 건수/파일 해시를 담는다.
- E3: 개발/운영 후보는 비슷한 원본 데이터가 있어도 스키마·이력·알림·legacy activity_recovery가 다르다. 폴더 이름이나 건수만으로 authoritative source를 선택할 수 없다.
- E4: 기존 Brain 아키텍처 AD-10은 SQLite 원본과 Postgres 복제를 전제한다. 기존 이니셔티브의 LLM 호출0 규칙은 대화/문서 수집을 대상으로 하며, 선택 Garmin AI 분석과 후속 채널 에이전트 기능의 적용 범위를 명시적으로 조정해야 한다.
- E5: compose.test.yaml은 tmpfs의 일회성 테스트 DB다. 제품 PostgreSQL에는 영속 볼륨을 쓰는 별도 구성이 필요하다. pgvector는 현재 필수 기능이 아니다.
- E6: 기존 Python의 tests/test_acceptance_report.py는 fake Codex E2E다. README의 실제 Codex 인수 테스트 설명과 다르므로, 그 테스트만으로 실제 모델 분석 품질을 입증하지 않는다.

## 아직 결정하지 않은 것

- PostgreSQL 안의 공통/확장 schema·테이블 이름, migration 버전 추적 구조.
- TypeScript↔Python 실행/저장 포트와 설정 전달 형식. Postgres 컨테이너 사용이 Python worker까지 컨테이너로 옮긴다는 뜻은 아니다.
- 개발/운영 DB 중 기준과 충돌 처리. 준비 단계에서는 모두 별도 출처로 보존했다.
- 채널 양방향·선제 메시지 기능의 출시 순서. 초기 흡수는 채널 계약을 마련하고 기존 발신 동작을 공통 경로에 편입하며, Slack 전체 구현을 암묵적 완료 조건으로 삼지 않는다.
- 현지 시각 예약의 시간대 변경·놓친 실행 정책과 작업별 진행 정체 판단 기준.
