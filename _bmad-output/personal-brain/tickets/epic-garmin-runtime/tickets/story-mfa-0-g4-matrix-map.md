## 기준 및 증거의 한계

조사 시작 `git rev-parse HEAD`의 full canonical SHA는 **`1d4fec9a16056b0f473967fb6fcaca8a8f37790d`**다. 원래 전체 변경 검토 기준은 계획에 남은 `885ad522e5a30b820c12f984959c03c98ca28bc1`이며, 현재 HEAD를 원래 수락 범위의 대체 기준으로 삼지 않는다.

같은 checkout을 구현자가 편집 중이다. 시작부터 계획·native·TS·시험 파일의 tracked 수정과 untracked 신규 파일이 존재했다. 아래는 HEAD에 고정된 tree가 아니라 순차적으로 읽은 dirty working tree의 관찰이며, 한 시점의 원자 snapshot도 아니다. 특히 `check-composed-auth.sh`, `composed-*`, `submission-*`, `supervisor-*.c`, `gui-*`, `broker-store.*` 등 신규 소스의 존재는 커밋·빌드·실행 가능성의 증거가 아니다. 끝에 다시 읽은 HEAD와 주요 파일 해시를 남기되 그것이 앞선 읽기를 원자적으로 고정하지는 않는다. D6 실행자는 구현자 checkpoint 후 정확한 commit/diff와 파일 해시를 다시 묶어야 한다.

시험·빌드·네트워크·OS 인증·운영 DB/tokenstore·설치·배포는 실행/접근하지 않았다. 소스·시험·계획을 수정하지 않았고 추가 워커나 build/review 스킬을 실행하지 않았다. 유일한 작성물은 이 `/tmp` 보고서다. 과거 계획/보고의 ‘통과’ 문장은 실행 증거로 사용하지 않았다. **모든 행의 현재 실행 판정은 ‘미실행’**이며, ‘연결’은 assert/분기 조건의 정적 존재만 뜻한다.

검토한 계약은 `tickets/story-mfa-0-plan.md`의 두 intent-contract(초기 결정 및 마지막 제출별 승인 결정), T01–T28, `tickets/story-mfa-0-supervisor-security-review.md`의 §4 반례와 §6 추가 행렬이다. 여기서 `tickets/` 접두사는 `_bmad-output/personal-brain/tickets/epic-garmin-runtime/tickets/`다. 나중에 채택된 제출별 생체 승인 결정을 적용하며, 이전 보안 보고의 ‘미결정’ 표현이나 옛 코드 행 번호를 현재 상태 판정으로 복사하지 않았다.

## 수락 관찰의 공통 형식

실제 최외곽(outermost) 관찰은 제품 진입점 → 단일 `runSupervisor` → 보호 admission/OS child 기록 → bootstrap ACK → 특정 GUI instance → 제출별 승인/worker 수락 → 실제 전송 직전 intent → broker 전송 관찰 → DB 결과 → 종료/restart까지 이어진다. 단위 함수의 반환값, mock 호출 수, `recorded` 메시지, worker가 쓴 ‘success’, 파일에 쓴 `call` 한 줄은 각각 해당 층의 사실이며 실제 HTTP/생체/DB provenance의 대용물이 아니다.

각 합성 실행은 비밀 원문 없이 work/attempt/run, binding/package/connection 세대, launch lease, PID/PGID/boot/start, prompt/응답 세대/operation/ordinal, intent ID와 결과, broker가 관찰한 전송 시각·횟수, 종료 확인 상태를 대조하도록 한다. OS 생체 성공과 원격 login/profile/dump 성공은 별도 증거다. HTTP·DB·승인을 원자 처리했다고 기록하지 않으며 전송 뒤 불명은 uncertain으로 남긴다. 쓰기 tx 2초 상한 및 입력/HTTP 대기 중 tx 없음도 trace로 확인해야 한다.

## 구현자가 D6에 바로 적용할 연결 순서

1. **checkpoint와 관찰자 고정:** 같은 구현자의 checkpoint 후 canonical SHA/전체 diff/fixture flags·정확한 실행 명령·exit code를 묶는다. 표의 모든 행은 미실행에서 출발한다. 현재 HEAD나 옛 보고의 수동 ‘통과’를 자동 수락값으로 가져오지 않는다. 아래 조사 중 변경 추기의 CORE 분기도 함께 확인한다.
2. **기존 부품의 재사용:** frame/FD·phase/승인 단회성은 FD/N, fake library 내부 전송은 check_http_guard, 기존 보호 전이·clock/budget는 P, 실제 daemon crash marker는 VP(garmin-protection), protected role/native 조립은 CPG를 사용한다. 각각의 관찰 층을 그대로 표시하고 하나의 성공으로 다른 층을 덮지 않는다.
3. **보호 제품 종단 연결:** `runSupervisor`의 protected admission→bootstrap.authorize→native supervisor/host/broker/GUI→worker FD5·제출 수락→pinned library→HTTP broker→protected DB를 한 attempt tuple로 묶는다. `composed-supervisor.c`의 별도 main 성공을 TS 제품 조립 증거로 대신하지 않는다. 현재 읽은 `src/auth.py:main`의 고정 `AUTH_PEER_UNVERIFIED`는 정상 인증 완료 시험이 아니라 실패 닫힘 회귀 기준이다.
4. **새 관찰을 붙일 우선 위치:** intent/결과 commit 직후·send 전 barrier(T19/T20/T21), canonical binding 전환 잠금 경합(T14/T26), null-key/세대 merge 반환값과 launcher 경계(T16), dump 후 verifier/evidence 저장(T25), verify HTTP 실제 전송/redirect/refresh(T09/T18/T27/T28), callback/consume/write/HTTP별 revoke(T10/T11 및 추가 묶음). 모두 기존 T를 보강하는 작업이며 범위를 대체하지 않는다.
5. **OS 실증을 별도 묶음으로 유지:** 실제 생체·AX·same UID/별도 UID·봉인/주입 방지·tokenstore·권위 OrbStack/관리 경로·OS egress·restart/group는 지원되는 격리 실기에서 별도 기록한다. 실증이 아직 없으면 해당 셀은 미검증이며 production auth/HTTP의 실패 닫힘 회귀를 함께 유지한다. 실제 계정·운영 tokenstore·배포/이전은 계획대로 16.9에 남는다.
6. **종료 증거와 정리:** barrier 해제→해당 합성 child/group만 종료·reap→daemon abort/await→store.close→fixture cleanup을 보존한다. trigger/EXECUTE 권한 주입 복원도 기록한다. host/broker가 연락 불명일 때 cleanup 완료나 신규 attempt 허용으로 기록하지 않는다. 테스트 도중 시간 제한·skip·지원 불가도 성공 대신 별도 결과로 기록한다.

이 조사 완료는 D6 연결 지도 작성 완료만 뜻한다. D6 실행·전체 수락·독립 리뷰·D7/16.9 완료를 뜻하지 않는다.
