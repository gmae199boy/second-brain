# Product Brief: Personal Brain

**관련 문서**: V1 slice 1의 요구사항은 `../prd-brain-v1-slice-1/prd-brain-v1-slice-1.md`(이 brief와 다르면 PRD가 최신이다). 상세 근거·접은 대안·시험 이력은 `addendum.md`, 전체 아키텍처 초안은 `../inputs/personal-brain-final-architecture.md`. 시험 보고서 원본은 `~/.supermemory/test/REPORT.md`, `~/.hindsight-test/REPORT.md`, `~/.brain-baseline-test/REPORT.md`.

## Executive Summary

Personal Brain은 내가 쓰는 모든 AI 코딩 에이전트(Claude Code, Codex, OpenCode)와 작업 도구(Orca, Paseo)가 **같은 기억, 같은 세션 기록, 같은 작업 맥락**을 공유하게 하는 개인용 시스템이다. AI와 harness는 교체 가능한 worker이고, 기억과 상태는 Brain이 소유한다.

지금은 새 세션마다 규칙·최근 작업·문서 위치를 다시 넣어야 하고, 그 기억은 도구마다 따로 있다가 사라진다. Brain은 사람처럼 "어제 뭐 했지"에 답하고, 내가 "검색해"라고 지시하지 않아도 맥락을 알아서 넣는다.

Brain은 내 **제2의 뇌**다. 그래서 대화를 요약본으로 바꿔 저장하지 않고 **원문을 그대로 보존**한다. V1 slice 1은 원본 보존 + 작업 로그 + 조각 검색 + Claude Code 수집이다. 일하는 에이전트가 진행·결정·규칙·선호를 그 순간에 한 줄씩 적고, Brain 자체는 LLM을 부르지 않는다. 사전 시험에서 원문 조각 검색은 추출 기반 기억 엔진 두 종보다 높은 점수를 냈다.

## The Problem

- **세션마다 재주입.** 규칙 재주입, 작업 맥락 상실("내가 뭐 하고 있었더라"), 문서 탐색 — 이 세 가지가 비슷한 빈도로 일어난다.
- **기억이 도구에 묶여 있다.** Claude 메모리, Codex 메모리, Orca 세션은 각자 따로다. Claude로 조사하고 Codex로 리뷰시키려면 처음부터 다시 설명한다.
- **영속되지 않는다.** Orca 세션 검색은 workspace 삭제와 함께 사라진다. BMad 문서는 프로젝트별이고 적어 둔 것만 남는다.
- **대상이 개발만이 아니다.** 키보드, 여행, 운동, 개인 행정 같은 생활 영역도 같은 문제를 겪는다.

## The Solution

**세 층의 기억.** 위 층일수록 정확하고, 아래 층은 언제든 위에서 다시 만든다.

| 층 | 무엇 | 성질 |
|---|---|---|
| ① 원본 | 모든 대화 본문을 `messages`에 그대로. 도구 호출은 한 줄 요약만. harness·모델·세션 ID·기계·프로젝트 등 추적 정보 포함 | 절대 안 잃는다. 고쳐 쓰지 않는다 |
| ② 작업 로그 | 일하는 에이전트가 그 순간에 적는 한 줄: 진행, 결정(옛 결정은 지우지 않고 대체됨으로), 규칙(내 발화의 인용), 선호. 대화 원문에 이어져 있다 | 놓치면 안 되는 것. 규칙은 세션 시작에 주입, 나머지는 조회 |
| ③ 검색 색인 | 대화 조각 임베딩 + reranker | 손실 있음. 원본에서 재생성 |

- **Brain Core SDK**: 도메인 로직과 포트만 가진 수동(passive) 코어. 타이머·서버·프로세스를 소유하지 않는다.
- **Runtime**: Core와 Infrastructure를 명시적으로 조립해 실행하는 쪽(host). 시험 단계는 스크립트·CLI, 운영 단계는 집 Mac mini의 데몬이고 그 위에 앱·CLI·모바일 client가 붙는다.
- **범위**: 맨 위는 나다. 나 ⊃ 워크스페이스 ⊃ 프로젝트 ⊃ 워크트리 ⊃ 세션. 모든 기록은 항상 나에 속하고 아래 수준은 자동으로 붙는 꼬리표다. 칸막이가 아니라 조회를 좁히고 넓히는 손잡이다.
- **자동 맥락 주입**: 세션이 시작될 때 Brain이 규칙과 최근 작업 로그 몇 줄만 넣는다. 프롬프트마다 넣지 않는다. 그 밖의 과거는 요청할 때 작업 로그(대분류) → 조각(소분류) → 원문으로 **단계적으로 넓혀** 읽는다. 결과마다 출처(세션·날짜·위치)가 붙는다.
- **출처 추적**: 조각·요약·결정·규칙은 모두 근거 세션과 메시지 범위를 가리킨다.
- **harness별 adapter**: Claude Code, Codex, OpenCode 각각 얇은 수집 adapter가 세션을 Brain의 정규화된 메시지로 넣는다.

## What Makes This Different

- **Claude·Codex 자체 메모리와 다른 점**: harness에 묶이지 않는다. 도구를 바꿔도 기억·결정·작업 상태가 그대로다.
- **추출 기반 기억 엔진(Supermemory, Hindsight, Mem0)과 다른 점**: 그들은 LLM이 대화를 사실 문장으로 다시 써서 저장한다. 빠뜨리고(시험에서 확인) 통합 단계에서 고쳐 쓴다. Brain은 원문을 보존하고 색인만 그 위에 얹는다.
- **Orca 세션 검색과 다른 점**: Brain은 영속적이고, 도구와 무관하며, 맥락을 자동 주입한다.
- **BMad 문서와 다른 점**: BMad는 한 프로젝트에서 사람이 적어 둔 것만 남긴다. Brain은 모든 프로젝트의 모든 대화를 자동으로 남긴다. BMad 문서는 Brain의 가장 믿을 만한 자료로 색인한다.
- **솔직한 차별점**: 새로운 기술이 아니라 **소유권과 영속성**이다.

## Who This Serves

나(명훈) 한 사람. 여러 프로젝트(Acme, SideShop, Personal Brain, 기타 서비스)와 생활 영역을 동시에 다루는 1인 개발자. Claude Code·Codex·OpenCode를 번갈아 쓰고, Orca·Paseo를 harness로 쓴다. 두 번째 Mac과 집 Mac, 나중에 모바일에서 같은 Brain을 본다.

팀원과의 공유는 현 단계에서 배제한다. 나중에 하더라도 각자 실행하고 DB만 공유하는 정도로 본다.

## Success Criteria

- Claude Code 새 세션에서 "어제 뭐 했지?"라고만 해도 맞는 답이 나온다. 몇 년 전 것도 같은 방식으로 나온다.
- 내가 "검색해", "brain_context 불러와" 같은 지시를 하지 않는다.
- Claude에서 Codex로 작업을 넘길 때 다시 설명하지 않는다. (Codex 수집이 들어가는 다음 조각의 기준. slice 1은 구조만 준비한다.)
- 사전 시험 채점표(한국어 질문 10개)에서 7개 이상 정답. 기준선 측정은 10/10이었으나 조각 29개짜리 작은 코퍼스의 값이다. 실사용 데이터가 쌓이면 같은 채점표를 확장해 다시 잰다.
- 옛 결정이 사라지지 않는다. 바뀐 결정은 이전 결정을 가리키며 둘 다 조회된다.

## Scope

**사전 시험(완료, 2026-10-01~02)**: Supermemory 3회, Hindsight 2회, 추출 없는 기준선 1회. 결과는 Key Decisions와 `addendum.md` §9.

**V1 slice 1**:
- Core 포트: 세션·메시지·작업 로그 저장소, 색인·검색, 임베딩, 재순위
- Infrastructure: PostgreSQL(+pgvector), Qwen 임베딩, `qwen3-rerank`. LLM Worker 없음
- 수집: Claude Code adapter(hook). 대화 본문 + 도구 한 줄 메모 + 추적 정보. Codex, OpenCode는 다음
- 작업 로그: 일하는 에이전트가 진행·결정·규칙·선호를 그 순간에 기록
- 색인: 조각화·임베딩(LLM 없음)
- 세션 시작 시 자동 주입: 켜져 있는 규칙 + 최근 작업 로그 몇 줄 + Brain 사용 안내
- 에이전트용 도구(형태는 architecture에서: CLI, MCP): 시작 맥락, 시간 조회, 대분류·소분류 검색, 넓히기, 작업 로그 적기·고치기, 내보내기, 점검
- 시간 질의: "어제·지난주"를 날짜 범위로 바꿔 작업 로그와 세션을 조회. 기본은 나 전체

**명시적 제외(V1 slice 1 밖)**: 추출·통합 기억 엔진(Hindsight 등), LLM 세션 요약, 과거 세션 가져오기(저장 구조만 수용), 두 번째 기계, harness 원본 파일 보관, 데스크톱·모바일 앱, 데몬, 스케줄러, Telegram 알림·승인, Google Calendar, Graphify·Google Drive 탐색, 다중 사용자·인증, 동적 provider plugin.

|---|---|---|---|
| 기억의 구조 | 세 층: 원본 / 구조화 기록 / 검색 색인 | 제2의 뇌는 요약본이 아니다. 추출·통합은 빠뜨리고 고쳐 쓴다 | slice 1 |
| 검색 | 대화 조각(약 1,200자) 임베딩 → `qwen3-rerank` → 상위 5개 | 기준선 내용 8문항 8/8. 추출 누락이라는 실패 유형이 없음 | slice 1 |
| LLM 사용 | Brain은 LLM을 부르지 않는다. 기록은 일하는 에이전트가 그 순간에 작업 로그로(BMad memlog 방식) | 뒤에서 따로 요약하면 공수가 두 번이고 요약은 괄호·대비·수치를 떨어뜨린다(시험 확인). 추출 엔진은 세션 4개에 40회·96만 자 | slice 1 |
| 시간 질의 | 작업 로그와 세션을 날짜 범위로 조회(SQL). 기본은 나 전체 | 시험한 모든 기억 엔진이 0/2. 조회 경로 문제였음 | slice 1 |
| 규칙·결정·선호 | 작업 로그의 종류. 규칙은 내 발화의 인용이고 세션 시작에 주입, 결정은 대체 체인, 선호는 조회할 때만 | 에이전트가 규칙을 다시 쓰면 조건·수치가 빠지고 검증 없이 매번 주입된다 | slice 1 |
| 범위 | 나 ⊃ 워크스페이스 ⊃ 프로젝트 ⊃ 워크트리 ⊃ 세션. 전부 꼬리표 | 프로젝트에서 내린 결정이 나 자체의 결정일 수 있다. 코딩 전용이 아니다 | slice 1 |
| 주입 | 세션 시작에 규칙 + 최근 작업 로그 몇 줄만. 프롬프트마다 넣지 않음 | 컨텍스트 부담. 밀어 넣는다고 품질이 오른다는 증거 없음 | slice 1 |
| 영속성 | 전체를 Brain 없이 읽을 수 있는 형식으로 내보내고 되살릴 수 있다 | 기계 한 대·DB 하나가 단일 장애점 | slice 1 |
| ①층 범위 | 대화 본문 + 도구 호출 한 줄 + 추적 정보. harness 원본 파일은 보관 안 함 | 작고 단순. 도구 출력 내용은 포기 | slice 1 |
| 임베딩 | Alibaba Model Studio `qwen3.7-text-embedding`, 1024차원 | 다국어, 저렴, pgvector 인덱스 한도(2000) 안 | slice 1 |
| reranker | Model Studio 국제 리전 `qwen3-rerank` | 임베딩과 같은 키, 1.2~1.5초. 영어 reranker는 한국어를 망가뜨리고 로컬 다국어는 31초 | slice 1 |
| 저장소 | PostgreSQL + pgvector 하나 | 원본·구조화 기록·색인을 한 DB에. 별도 기억 서버 없음 | slice 1 |
| 추출·통합 엔진 | 쓰지 않음. 필요해지면 Hindsight를 `MemoryProvider` 뒤에 붙임 | Hindsight 7/10이나 주입 비용 큼. 원본이 있으니 나중에 넣을 수 있음 | 나중 |
| 실행 환경 | 집 Mac mini 단일 머신. 나중에 Tailscale로 두 번째 Mac이 세션을 밀어 넣음 | Tailscale로 두 Mac을 잇는다 | 다음 |
| 알림·승인 | 양방향 인터페이스, Telegram 먼저, 스케줄별 auto/ask | 앱 없이도 승인 가능 | 나중 |
| 앱 단계 구조 | Mac mini 데몬 = Runtime, 앱·CLI·모바일은 client | 항상 켜져 있어야 하는 일(스케줄, 승인, 원격 수집) | 나중 |

**제약·가정**: 운영 비용은 임베딩·rerank로 월 수 달러에서 수십 달러. rerank가 질의당 약 0.002달러라 주입 빈도에 비례한다. [ASSUMPTION] 하루 세션 10개, 주입 수백 회. 수치 근거는 `addendum.md` §9.

## Open Questions and Risks

- **규모**: 기준선은 조각 29개에서 잰 값이다. 조각 수천 개에서 같은 점수가 나오는지 미검증. 가장 큰 위험.
- **채점표의 편향**: 질문 10개는 조각 보존에 유리했다. 집계("몇 번 물어봤지"), 세션 간 변화("A에서 B로 바뀌었나"), 모순 해소("지금도 유효한가"), 시점 추론은 재지 않았다. 이 유형이 추출·통합 엔진의 존재 이유다. ②층(결정의 supersede 체인)이 얼마나 덮는지 실사용에서 확인한다.
- **에이전트가 실제로 적는가**: 작업 로그는 에이전트의 규율에 달려 있다. 로그가 한 줄 이상 있는 세션 80%, 결정이 로그에 적힌 비율 80%를 실사용에서 잰다. 못 미치면 안전망 요약이나 더 강한 수단(skill, plugin)을 연다.
- **조회 결과 크기**: 조각 5개가 약 8천 자로, 추출 기억보다 20~30배 길다. 요청할 때만 조회하므로 부담은 조회 횟수에 비례한다.
- **rerank 비용**: 후보 30개 기준 질의당 약 1만 8천 토큰. 후보 수 축소·본문 절단은 미검증.
- **대분류 먼저의 효과**: 작업 로그 → 조각의 2단계 조회는 재지 않았다. 기준선이 잰 것은 LLM 요약과 조각이다.
- **큰 메시지**: 메시지 하나가 조각 목표를 넘으면 2차 분할이 필요하다(시험에서 7,433자 조각이 상위를 독식).
- **Codex·OpenCode hook**: Claude Code와 같은 방식의 시작·종료 hook이 있는지 확인 필요. [ASSUMPTION] Codex는 UserPromptSubmit/Stop hook, OpenCode는 plugin으로 가능.
- **키 노출**: Model Studio API 키가 대화에 평문으로 들어간 적이 있다. 재발급 필요.

## Vision

내 모든 AI와 작업 도구가 같은 기억·상태·프로젝트 맥락을 공유하고, 나는 어떤 AI를 쓰는지 신경 쓰지 않고 이전 작업을 그대로 이어간다. Jira·Confluence·Drive·Google Calendar 같은 외부 서비스는 한 번의 integration으로 UI와 에이전트가 같이 쓰고, 스케줄러가 알아서 일하되 승인은 내가 한다.
